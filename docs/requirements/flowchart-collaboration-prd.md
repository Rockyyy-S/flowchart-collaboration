## 一、产品定义

### 1.1 产品名称（待定）

建议初期用工作名 **"Flowkit"** 或 **"流程驱动"**，后续上线前进行品牌命名。

### 1.2 一句话产品定义

**"流程图驱动的项目协作执行平台 — 用流程强约束 + 文档门禁 + 自动流转，确保项目不失控、不丢产出、不靠人催。"**

### 1.3 产品定位

- **非项目管理工具** (Jira/Asana/飞书项目 的替代)  
  vs.
- **是流程执行平台** + 项目协作系统的组合

**核心差异** | 
| 维度 | Jira/Asana | 本产品 |
|------|----------|--------|
| 流程模型 | 看板/任务列表 | 有向图 + 依赖验证 |
| 文档管理 | 附件关联 (弱) | 输入输出定义 (强约束) |
| 完成标准 | 人工勾选 | 自动门禁验证 |
| 使用场景 | 通用敏捷管理 | 规范性强、文档驱动的项目 |

### 1.4 目标用户画像（优先级排序）

#### P0: 研发部门 (最优先 - 上线第一个月主攻)
- **角色** | CTO、技术总监、研发项目经理
- **团队规模** | 20-200 人
- **核心场景** | 需求评审 → 技术方案评审 → 开发 → 测试 → 发布  
- **痛点** | 
  - 流程复杂；需求文档、技术文档、测试报告散落各处
  - PRD 评审效率低；进度难以可视化
  - 交付物常遗漏或版本混乱
  - 责任追踪困难，项目过程难以复盘
- **付费意愿** | ⭐⭐⭐⭐⭐ (极高)
- **月度客户价值** | 减少 20-30% 的流程评审时间；提升交付物完整性 15-20%

#### P1: 咨询/实施服务公司 (第二优先 - 第 2-3 个月)
- **角色** | 交付经理、质量经理
- **团队规模** | 10-100 人 (按项目组)
- **核心场景** | 客户交付、项目合规、多项目并行、变更追踪
- **痛点**  
  - 客户对交付物检查严格；合规性要求高
  - 流程必须可追溯（支撑 ISO 认证、客户审计）
  - 多项目并行时，优先级冲突频繁
- **付费意愿** | ⭐⭐⭐⭐⭐ (极高)
- **变现口径** | 按项目计费或按交付周期计费

#### P2: 制造业/硬件研发 (第三优先 - 第 3-4 个月)
- **角色** | 工艺设计、生产计划、质量部门
- **痛点** | 工艺流程、检验流程必须严格执行；文档必须完整
- **付费意愿** | ⭐⭐⭐⭐ (高)

#### P3: 政府/事业单位、设计/创意公司
- 后续扩展的垂直市场

## 二、核心价值主张

### 2.1 对管理者的价值

✅ **流程可见** | 项目在哪一步一目了然；进度透明  
✅ **规范性保证** | 流程强约束，不能跳步，关键文档必须完成才能流转  
✅ **责任明确** | 每个环节谁负责、什么期限、交付什么、一清二楚  
✅ **追踪审计** | 项目过程完整记录，支撑事后复盘、合规检查

### 2.2 对执行者的价值

✅ **清晰指引** | 知道自己在流程中的位置、需要交付什么、截止日期  
✅ **减少沟通** | 不用反复问"下一步是什么"，系统自动推送  
✅ **避免遗漏** | 文档门禁确保不会漏掉关键产出物  
✅ **任务聚焦** | 不用在 Jira + 飞书 + 钉钉 之间切换

### 2.3 对团队的价值

✅ **单一事实来源** | 所有流程、文档、状态在一个平台  
✅ **自动化驱动** | 流程完成 → 自动通知下游 → 自动记录，不需要人工催促  
✅ **代际传承** | 流程模板沉淀后，可复用于后续类似项目  
✅ **决策支持** | 提供流程数据分析：哪些环节常见瓶颈、平均周期多久、延期原因

## 三、核心功能设计

### 3.1 产品四大支柱模块

```
┌────────────────────────────────────────────────┐
│  模块一：流程图编辑器（核心交互）               │
│  - 拖拽式节点创建、连线                       │
│  - 并行子流程、条件分支支持                   │
│  - 节点详情右侧面板配置                       │
└────────────────────────────────────────────────┘

┌────────────────────────────────────────────────┐
│  模块二：环节管理与门禁引擎（核心逻辑）         │
│  - 状态机管理：待启动→可开始→进行中→待确认→已完成 │
│  - 门禁检测：文件存在性、数量、内容校验 (分级) │
│  - 并行子流程自动汇总                         │
└────────────────────────────────────────────────┘

┌────────────────────────────────────────────────┐
│  模块三：文档存储与协作（收费点）               │
│  - 项目工作空间（文件夹+权限）                │
│  - 版本管理、在线预览、权限控制                │
│  - 外链支持（但不参与门禁检测）               │
└────────────────────────────────────────────────┘

┌────────────────────────────────────────────────┐
│  模块四：通知与审计（运营驱动）                │
│  - 自动流转通知、截止前提醒、逾期告警         │
│  - 审计日志、流程执行报表                     │
│  - 企业 IM 集成（钉钉/飞书/企业微信）        │
└────────────────────────────────────────────────┘
```

### 3.2 详细功能清单

#### A) 流程图编辑器

**节点类型** (5 种):
- **普通环节** | 单一流程步骤，需配置目标、负责人、期限、输入输出物
- **并行子流程** | 包含多个独立并行的子节点，所有子节点完成后汇总
- **条件分支** | 根据条件判断流向（如产品设计方案有"复杂"vs"简单"两条路）
- **汇总节点** | 合并多条并行线的输出，进行集中门禁检查
- **开始/结束节点** | 流程的入口和终点

**交互能力**:
- 拖拽创建节点，自动吸附对齐
- 连线表示依赖关系，单击显示连线属性
- 双击节点进入详情编辑（设置角色、输出物、门禁等）
- 右侧详情面板折叠/展开，不影响画布显示
- 缩放、平移、迷你地图快速导航
- 右键节点呼出快捷菜单（标记完成、查看文档、分配人员）

**关键设计哲学** | "一眼看懂流程，细节收在侧边栏里"

#### B) 环节管理 (每个环节必须包含以下配置)

**基础信息**:
```yaml
环节名称: "需求评审"
环节目标: "完成产品需求文档评审并确认开发范围"
环节类型: "普通任务" | "并行子流程" | "分支" | "汇总"
截止时间: "2026-05-15"
```

**角色与责任**:
```yaml
角色分配:
  - 角色: "产品经理"
    具体人: "张三"
    职责: "撰写PRD、组织评审会、整合反馈"
    权限: "编辑PRD、批准进入下一环"
  
  - 角色: "技术负责人"
    具体人: "李四"
    职责: "评估技术可行性、提出架构建议"
    权限: "查看PRD、提交技术评估意见"
    
  - 角色: "测试负责人"
    具体人: "王五"
    职责: "参与评审、确认测试用例编写范围"
    权限: "查看PRD、查看评审记录"
```

**输入输出物配置**:
```yaml
输入物: 
  - "产品提案.docx" (来自上个环节)
  - "市场调研报告" (可选，来自需求部门)

输出物:
  - name: "PRD v1.0"
    type: "内部文档"
    required: true        # 门禁：必须有
    location: "系统存储"
    
  - name: "技术可行性评估"
    type: "内部文档"
    required: true
    location: "系统存储"
    
  - name: "设计原型"
    type: "外链"
    required: false       # 可选
    location: "Figma"
```

**门禁规则配置** (分级能力):
```yaml
基础门禁 (免费版支持):
  - 必须上传"PRD v1.0"文件
  - 必须上传"技术可行性评估"文件
  
规则门禁 (Pro 版支持):
  - 文件数量 >= 2
  - 文件类型: PDF / Word (非纯图片)
  - 文件大小: > 100KB (防止空壳文档)
  - 命名规范: 必须包含版本号 (v1.0, v1.1 等)
  
业务门禁 (Enterprise 版支持):
  - PRD 必须包含【验收标准】章节 (内容校验)
  - 技术评估报告必须有"可行性结论"字段
  - 需要产品经理和技术负责人双重确认
```

**状态机**:
```
┌─────────┐
│ 待启动   │  (等待前置环节完成)
└────┬────┘
     │前置环节完成
     ▼
┌─────────────┐
│ 可开始      │  (灰显、不可交互，等待执行人点击"开始")
└────┬────────┘
     │执行人点击"开始"
     ▼
┌─────────────┐
│ 进行中      │  (蓝色高亮、可上传文档)
└────┬────────┘
     │执行人点击"标记完成"
     ▼
┌──────────────┐
│ 门禁检查中   │  (系统自动验证输出物)
└────┬─────────┘
     │
     ├─ 通过 ──→ ┌─────────────┐
     │           │ 子流程完成中  │ (若有子流程)
     │           └──────┬──────┘
     │                  │所有子流程完成
     │                  ▼
     │           ┌─────────────┐
     ╰──────────→│ 已完成       │ (字体灰色、勾选图标)
                 └─────────────┘
     
     ├─ 失败 ──→ ┌──────────────────────┐
                 │ 待补齐                 │
                 │ (红色提示：缺少PRDv1.0) │
                 └─────────┬──────────────┘
                          │补要上传缺失文件
                          ▼
                          再试一次
```

#### C) 并行子流程

**设计思路** | Fork-Join 模型 (分叉-汇合):
- 一个主环节下可添加多个并行子流程
- 子流程可嵌套 (支持三层以上嵌套，但不建议超过 3 层)
- 所有子流程完成 + 各自门禁通过 → 主环节自动标记"已完成"

**示例**:
```
主环节: "产品设计"

├─ 子流程1: "UI 视觉设计" (由设计师负责)
│  └─ 快速评审 → 输出物: 视觉稿 v1.0 (必填)
│  └─ 详细评审 → 输出物: UI组件库 (可选)
│  └─ 确认定版 → 输出物: 最终设计文档 (必填)
│
├─ 子流程2: "交互设计" (由交互设计师负责)
│  └─ 原型设计 → 输出物: 原型文件 (必填)
│  └─ 可用性测试 → 输出物: 测试报告 (必填)
│
└─ 子流程3: "产品需求梳理" (由产品经理负责)
   └─ 功能清单 → 输出物: 功能清单.xlsx (必填)
   └─ 用户故事 → 输出物: 用户故事卡.md (必填)

当三个子流程都完成后 → 主环节自动完成，流转给【开发】环节
```

#### D) 文档存储与工作空间

**项目工作空间结构**:
```
项目名: "ProductName v1.0"
│
├─ 📁 需求阶段
│  ├── PRD v1.0.docx
│  ├── PRD v1.1.docx (版本历史)
│  └── 市场调研.pdf
│
├─ 📁 设计阶段
│  ├── UI 视觉稿.fig
│  ├── 原型设计.xd
│  └── 设计规范.md
│
├─ 📁 开发阶段
│  ├── 技术方案.md
│  ├── API 文档.md
│  └── 数据库设计.sql
│
├─ 📁 测试阶段
│  ├── 测试计划.xlsx
│  ├── 测试用例.xlsx
│  └── 测试报告.docx
│
└─ 📁 发布阶段
   ├── 发布清单.md
   └── 发布验收报告.md
```

**文档功能特性**:
- 自动版本管理：每次更新保存历史版本，支持版本对比、回滚
- 在线预览：PDF、Word、Excel、PPT、Markdown、图片原生预览
- 权限控制：按角色设置查看/编辑/下载的权限
- 外链支持：可关联 Figma、Notion、Google Docs、GitHub 链接（但外链不参与门禁检测）

**与门禁的关联**:
- 环节配置中的"输出物"直接绑定到工作空间的文件
- 系统实时检查文件存在性（不仅是 URL 检查）
- 文件被删除/移到回收站时，关联的环节收到警告

#### E) 通知系统

**自动通知触发事件**:

| 事件 | 通知对象 | 通知内容示例 | 渠道 |
|------|--------|----------|------|
| 前置环节完成 | 下一环节所有执行人 + 项目负责人 | "【需求评审】已完成，请开始【技术方案设计】。截止日期：2026-05-25" | 站内 + 邮件 + IM |
| 门禁未通过 | 当前环节执行人 | "【技术方案设计】缺少输出物「技术架构图」。请补充后再提交。" | 站内 + 邮件 |
| 截止日期前 24h | 环节执行人 (未完成时) | "【UI 设计】距离截止时间还有 1 天" | 站内 + 邮件 |
| 环节逾期 | 环节执行人 + 项目负责人 + 上级 | "【后端开发】已逾期 3 天，当前影响总进度 5 天" | 站内 + 邮件 + IM |
| 子流程全部完成 | 下一环节负责人 + 项目负责人 | "【产品设计】所有 3 个子任务已完成，可进入【开发】阶段" | 站内 + IM |

**通知优先级**:
- 🔴 高优先 | 门禁失败、环节逾期 → 实时推送 (立即)
- 🟡 中优先 | 前置环节完成 → 立即推送
- 🟢 低优先 | 截止前提醒 → 定时推送 (前 24h)

**通知渠道** (可配置):
1. 站内通知 (必默认) | 右上角铃铛 + 未读数角标
2. 邮件通知 (默认开启) | 支持每日摘要或实时通知
3. 企业 IM 集成 (Pro+ 版) | 钉钉、企业微信、飞书、Slack

### 3.3 辅助功能 (MVP 不包含，后续版本)

#### 流程模板市场
- 预设 30+ 行业标准流程模板（研发、市场、咨询、制造等）
- 支持团队上传私有模板，供内部复用
- 模板支持参数化配置（如环节数、角色等）

#### 数据分析报表
- 流程耗时分布：平均多久完成一个环节
- 瓶颈识别：哪些环节常见延期，原因分析
- 文档完整度：输出物缺失率统计
- 人均负载：每个人平均负责多少环节

#### AI 辅助
- 根据项目类型自动推荐流程模板
- 智能检测文档是否符合规范（如 PRD 是否包含【验收标准】）
- 流程建议：根据项目复杂度建议环节数和并行度

### 4.2 交互设计原则

#### 易用性目标
- **3 分钟内** 创建一个项目流程
- **10 秒内** 理解一个节点的配置和状态
- **1 次点击** 完成一个节点确认

#### 亮点交互
| 交互 | 说明 |
|------|------|
| **拖拽建图** | 左边栏拖拽节点到画布，自动吸附对齐 |
| **实时反馈** | 节点完成时轻微缩放动画 + 字体灰色渐变 |
| **"三层架构"** | 流程全景图 → 节点详情 → 输出物列表（逐层展开） |
| **右键快捷** | 右键节点呼出菜单（标记完成/查看文档/分配人员） |
| **自动聚焦** | 点击通知消息，自动跳转到相关环节 |
| **门禁提示** | 门禁失败时，红色高亮缺失项，并提示"谁负责补齐" |

### 4.3 视觉风格

- **配色** | 主色深靛蓝 (#4F46E5) + 成功绿 (#10B981) + 警告黄 (#F59E0B)
- **排版** | 清晰的信息层级；足够的白空间
- **动画** | 轻微、不骚扰的过渡效果

## 六、技术架构

### 6.1 技术选型方案（综合对比）

#### 前端层

| 技术 | 选择 | 理由 |
|-----|-----|------|
| 框架 | React 18 + TypeScript | 生态最成熟；组件化能力强；团队经验丰富 |
| 状态管理 | Zustand | 轻量、简洁；比 Redux 适合高频交互 |
| 流程图引擎 | **LogicFlow** (优先) 或 React Flow | LogicFlow 是阿里开源、专为业务流程优化、国产支持好 |
| UI 组件库 | Ant Design v5 | 企业级、完整、中文文档好 |
| 样式 | TailwindCSS | 原子化 CSS、快速构建现代界面 |
| 构建工具 | Vite | 开发快、打包快 |

**流程图引擎详细对比**:

| 对比项 | LogicFlow | React Flow |
|------|----------|-----------|
| 出品 | 阿里（国产） | 国外社区 |
| 插件化 | ✓ 强 | △ 中等 |
| 子流程 | ✓ 原生支持 | ✗ 需自己封装 |
| 教程文档 | ✓ 中文齐全 | ✓ 英文齐全 |
| 学习成本 | ✗ 较高 | ✓ 较低 |
| 社区活力 | △ 中等 (GitHub ~10k star) | ✓ 高 (GitHub ~40k star) |
| 建议 | **MVP 首选** (功能齐全、减少二次开发) | 备选 (生态成熟，但需要自己扩展) |

**推荐方案** | **MVP 阶段用 LogicFlow**（功能完整、快速上线）；后续可考虑迁移到 React Flow（社区成熟、长期维护）

#### 后端层

| 技术 | 选择 | 理由 |
|-----|-----|------|
| 语言 | Node.js + TypeScript | 与前端同语言，全栈统一；开发效率高 |
| 框架 | NestJS | 模块化、依赖注入、类型安全、适合中大型系统 |
| 数据库 | PostgreSQL | 关系型数据好；JSONB 字段灵活；支持行级权限 |
| 缓存 | Redis | 通知队列、会话存储、状态缓存 |
| 文件存储 | MinIO (自建) 或阿里云 OSS | MinIO S3 兼容、可私有部署；OSS 成本低 |
| 消息队列 | RabbitMQ 或 Redis Streams | 通知系统异步处理 |
| 实时协作 | WebSocket (Socket.io) | 环节流转实时推送 |
| API 规范 | REST + GraphQL (可选) | REST 调试简单；GraphQL 复杂查询灵活 |

#### 基础设施

| 组件 | 选择 | 说明 |
|-----|-----|------|
| 容器化 | Docker | 开发和生产环境一致 |
| 编排 | Kubernetes (可选) | 企业版支持；初期可用 Docker Compose |
| 监控 | Prometheus + Grafana | 开源方案，社区支撑好 |
| 日志 | ELK Stack 或 Datadog | 用于故障排查和审计追踪 |

### 6.2 核心数据模型

**简化 ER 模型** (关键表):

```sql
-- 项目表
CREATE TABLE projects (
  id UUID PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  description TEXT,
  flow_structure JSONB,      -- 存储流程图的完整结构 (LogicFlow 导出)
  status VARCHAR(50),         -- active / archived / draft
  created_by UUID,
  created_at TIMESTAMP,
  workspace_id UUID
);

-- 环节执行状态表
CREATE TABLE node_executions (
  id UUID PRIMARY KEY,
  project_id UUID REFERENCES projects(id),
  node_id VARCHAR(100),      -- 对应 flow_structure 中的 node id
  status VARCHAR(50),         -- pending / in_progress / completed / blocked
  assigned_to UUID[],         -- 执行人 ID 数组
  started_at TIMESTAMP,
  completed_at TIMESTAMP,
  created_at TIMESTAMP
);

-- 输出物与门禁表
CREATE TABLE node_artifacts (
  id UUID PRIMARY KEY,
  node_execution_id UUID REFERENCES node_executions(id),
  artifact_name VARCHAR(255),
  artifact_type VARCHAR(50),  -- internal / external
  is_required BOOLEAN,
  document_id UUID REFERENCES documents(id),  -- 若是内部文件
  external_url VARCHAR(1000),                 -- 若是外链
  validation_status VARCHAR(50),  -- pending / valid / invalid
  created_at TIMESTAMP
);

-- 文档表
CREATE TABLE documents (
  id UUID PRIMARY KEY,
  workspace_id UUID,
  name VARCHAR(255),
  file_path VARCHAR(1000),    -- MinIO 存储路径
  file_size BIGINT,
  mime_type VARCHAR(100),
  version INTEGER,
  created_by UUID,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

-- 审计日志表
CREATE TABLE audit_logs (
  id UUID PRIMARY KEY,
  project_id UUID,
  action VARCHAR(100),        -- node_completed / document_uploaded / gate_passed 等
  actor_id UUID,
  details JSONB,
  created_at TIMESTAMP
);
```

### 7.3 衡量 MVP 成功的关键指标

| 指标 | 目标 | 说明 |
|------|------|------|
| **用户能在 5 分钟内创建流程** | > 60% 首次用户成功 | 衡量易用性 |
| **首周续费率** | > 40% 试用用户升级付费 | 衡量产品价值 |

| **支持问卷** | > 100 用户有效使用 (含试用) | 达成小规模验证 |

## 八、风险与应对

### 8.1 核心风险清单

| 风险 | 概率 | 影响 | 应对方案 |
|------|------|------|--------|
| 销售周期长 | 60% | 高 | 从中型企业(50-500人)切入；提供试点模式 |
| 用户教育成本高 | 70% | 中 | 投资培训视频、案例库、在线课程 |
| 竞争对手复制 | 50% | 中 | 快速积累用户数据；构建行业模板护城河 |
| 流程过于严格引起反感 | 40% | 中 | 支持"柔性模式"（门禁可设为警告） |
| 文档存储盈利不达预期 | 45% | 低 | 不强行依赖存储收入；以流程 + 门禁为核心 |

### 8.2 早期验证方案

**建议立即启动** (不依赖开发):

1. **深度用户访谈** (Week 1-2, 进行中)
   - 样本：15-20 个符合目标用户的企业 CTO / PM / 项目经理
   - 核心问题：
     - "目前流程不规范导致的成本有多大？"
     - "你愿意为流程规范化工具付费吗？月预算是多少？"
     - "相比 Jira/飞书，新工具的核心吸引力是什么？"
   - 产出：需求澄清 + 商业可行性证据
   
2. **竞争对手深度分析** (Week 2)
   - 对标 Jira 工作流、Asana Custom Fields、飞书项目的"流程化"能力
   - 评估："竞争对手多久能复制我们的核心功能？"
   
3. **原型可用性测试** (可选，Week 3-4)
   - 用 Figma 画出 MVP 的 3-4 个核心页面高保真原型
   - 邀请 5-8 个目标用户测试
   - 关键指标：5 分钟内完成第一个流程图（成功率 > 60%）

- 业务门禁（内容校验、多步审批）
- 数据分析与报表
- API 开放平台
- 私有部署选项

## 十、验收标准 (DoD - Definition of Done)

### 功能验收标准

✅ **流程图编辑器**
- [ ] 可拖拽添加 5 种节点类型
- [ ] 可连接节点表示流向
- [ ] 支持节点双击编辑、右键删除
- [ ] 支持缩放、平移、迷你地图导航
- [ ] 流程图数据可导出为 JSON（便于版本控制）

✅ **环节管理**
- [ ] 每个环节可配置：名称、目标、截止时间、负责人、输出物
- [ ] 支持多人分配、角色配置
- [ ] 支持查看输入物来源
- [ ] 状态机正确流转（待启动 → 可开始 → 进行中 → 待确认 → 已完成）

✅ **基础门禁**
- [ ] 环节点击"完成"时自动检查必需输出物是否存在
- [ ] 检查失败时弹出明确提示（缺什么、谁负责补齐）
- [ ] 支持补齐后重新提交

✅ **文档上传**
- [ ] 支持拖拽上传、多文件上传
- [ ] 支持与环节输出物关联
- [ ] 文件详情页可查看上传人、上传时间、版本号
- [ ] 支持文件删除（会触发环节预警）

✅ **自动通知**
- [ ] 前置环节完成 → 下一环节自动收到站内通知
- [ ] 环节执行人变更 → 通知新执行人
- [ ] 门禁失败 → 通知相关人员缺失内容
- [ ] 邮件通知模板清晰、可配置每日聚合

✅ **项目看板**
- [ ] 流程进度条显示（n / total 环节完成）
- [ ] 选中环节后显示详情和关键信息
- [ ] 支持按环节状态筛选（未开始/进行中/已完成）

### 性能验收标准

✅ 流程图加载时间 < 3s (500+ 节点)  
✅ 文件上传 < 30 秒 (100 MB 以内)  
✅ 通知推送延迟 < 5 秒  
✅ 页面响应时间 < 1 秒  

### 安全验收标准

✅ 所有 API 需身份认证（JWT Token）  
✅ 文件存储端点需权限校验  
✅ 敏感操作（删除项目/流程）需二次确认  
✅ 审计日志完整记录所有写操作
